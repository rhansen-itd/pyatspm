  <details><summary>Original entry</summary>

  `.datZ` time offsets are measured from the *header* instant (`Controller Data Log Beginning:,<M/D/YYYY>,<HH:MM:SS.s>`), which sits 0.0–1.0 s past the filename's clock boundary. `_parse_filename_timestamp` (`data/ingestion.py:283`) yields only the boundary, and that is what reaches `parse_datz_bytes` (`ingestion.py:479`) as `base_timestamp` (`analysis/decoders.py:143`), so every stored event is early by that offset — mean 0.52 s, and a full 1.0 s on 38% of files. Within-file durations are unaffected (uniform shift cancels); **cross-file-boundary durations are wrong by `delta_prev − delta_next`, up to ±1.0 s**, which hits detector occupancy and any phase interval spanning a file edge. Verified two independent ways over the 14,124-file corpus: the offset cap tracks the header offset exactly (`cap = nominal_ds − 1 − 10·delta`, never exceeded), and 6,495 of 6,503 cross-boundary yellow/red-clearance intervals show a residual equal to `delta_prev − delta_next` (the 8 misses are site-315 phases on alternate timing plans; zero exceptions on either 15-minute site). Fix: parse the header line in `parse_datz_bytes` and add its seconds-plus-fraction to the base. Take only the *delta*, not the absolute header time — it needs no timezone, so the functional core stays pure. Two constraints for whoever picks this up: (1) **do not shift `utc_start` itself** — it is the grid anchor for `ingestion_log` spans, `_calculate_duration`/`_grid_duration` (`ingestion.py:512`), gap detection, and cycle-processing ranges, all of which legitimately want the boundary; only the event base moves. (2) The no-header path must stay a supported fallback — `_make_datz` in `tests/analysis/test_decoders.py:40` builds buffers with no `Controller Data Log Beginning` line, so falling back to the supplied base keeps every existing decoder test green. Worth exposing a `parse_datz_header()` helper so the shell can cross-check header `HH:MM` against the filename and warn on disagreement; that check is also a free off-grid-file detector. Checked: the ≤1.0 s shift cannot flip the 61 s Grid-Mode heuristic (worst case 58.9 s → 59.9 s, 1.1 s headroom). Small, Sonnet-sized. Gated on the backfill decision below only for already-ingested DBs — the code fix stands alone.

- ~~**Out-of-order timestamps from a backward clock set are ingested silently.**~~ **Done** — `_fence_clock_steps` (`data/ingestion.py`) runs in the shell right after `parse_datz_bytes` returns, while the rows are still in file order, and inserts an `event_code = -1` marker per backward step via the existing `insert_gap_marker`, so every duration/pairing consumer stops at the break per CLAUDE.md §5. Detection is `np.diff(timestamps) < 0` within the file, plus a cross-file check for a break that straddles an edge. **Marker placement settled at 0.05 s below the first post-step event** (`_CLOCK_STEP_MARKER_LEAD`): binary offsets are whole deciseconds off a common per-file base, so half a decisecond can never land on a real event, always sorts immediately ahead of the one it fences, and avoids the collision the existing `prev + 0.1` gap placement would hit inside a replayed band. Deliberately **one marker per step, at the band start, not two** — post-step events are internally consistent and correctly ordered among themselves, so a second marker at the band end would break a genuinely valid pair; only the pre/post interleaving needs fencing. The count surfaces as `clock_steps` in `get_ingestion_stats()` and as `Clock steps back` in the ingest summary, kept separate from `gap_markers` (which stays the database-wide `event_code = -1` total, these included) so clock sets don't blend into comms-gap noise. The cross-file check is guarded on the *previous file's boundary* rather than its last event, because in Gap Fill the last file processed can legitimately sit later on the clock — an unguarded comparison flags ordinary backfill; note also that a well-formed file's offsets never reach the next boundary, so in practice that arm fires on spill-over from an anomalous predecessor (off-grid header, edge-landing set) rather than on a clean straddle. Verified with the shipped detector over the full 14,124-file / 6.72 M-event corpus: **0 files flagged**, matching the predicted zero-false-positive rate. Verified end-to-end on real `.datZ` files with a deliberate −5 s set injected mid-file (offsets replaying a 5.0 s band, mirroring the hardware case): the step was caught and warned about, the marker landed 0.05 s below the first post-step event with **0 collisions** against real rows, and all 1,075 events were still stored — fencing loses no data. Covered by `tests/data/test_ingestion_clock_steps.py` (marker value and sort position, multiple steps, warning text, cross-file edge, Gap-Fill backfill not flagged, comms gap not miscounted, chronological/single-event/empty files silent). Still does **not** restore order or rescue rows lost to `UNIQUE(timestamp, event_code, parameter)` — both belong to the future item below.

  <details><summary>Original entry</summary>

  A backward controller clock adjustment makes the recorded time *decrease* part-way through a file: the offsets replay a band, so events from two different real moments carry the same labels and, sorted by time, land in the wrong sequence. Confirmed on hardware 2026-07-29 — a deliberate −5 s set on 10.70.10.51 produced offsets `310 → 262` inside `ECON_10.70.10.51_2026_07_29_1630.datZ`, replaying a 4.8 s band. Simulated against the real corpus, a 5 s backward set puts **~12 events (site 201) to ~21 events (site 315) out of order**, and yields impossible sequences — a detector actuating while already active, an off with no on. Nothing downstream expects this: `_build_detector_df`/`_build_signal_df` sort by timestamp then pair adjacent rows, and `merge_asof` requires sorted keys. Fix: after `parse_datz_bytes` returns, check for a decreasing timestamp (`df['timestamp'].diff() < 0`) and, where found, insert an `event_code = -1` marker via the existing `insert_gap_marker` so every duration/pairing consumer stops there per CLAUDE.md §5. Do the check in the shell (`_process_file`, `data/ingestion.py:447`) rather than the decoder — it needs no signature change and no new public export, and marker insertion already lives there. Also compare each file's first timestamp against the previous file's last, to catch a set that straddles a file boundary. Detection is essentially free of false positives: **zero backward steps in all 14,124 corpus files** of normal operation, because the logger appends chronologically and time cannot otherwise go backwards. Two things this deliberately does *not* do, both belonging to the future item below: it does not restore the correct order (the marker only prevents measuring *across* the break), and it does not rescue rows lost to `UNIQUE(timestamp, event_code, parameter)` — measured at ~0.1–0.2 events per backward set, ~1% of affected events. Worth surfacing the count separately from ordinary gap markers in the ingest summary so these are visible rather than blending into comms-gap noise. One judgement call for whoever picks this up: the marker timestamp. Existing markers use `prev_last_event_ts + 0.1`, but inside a replayed band that value can collide with a real event, so pick the placement deliberately. Tests are easy — the binary format takes any `uint16` offset, so a synthetic buffer with decreasing offsets exercises it directly. Small, Sonnet-sized.

  </details>
- ~~**`resolve_stopbar_target` has no phase-number range check.**~~ **Done** — it now rejects any integer outside `MIN_PHASE_NUMBER`-`MAX_PHASE_NUMBER` (1-16) with a distinct `"out of range"` `ValueError`, separate from the existing `"Unrecognised stopbar phase field"` raised for non-numeric, non-overlap input. **Bound to 16 deliberately, not to a per-intersection config lookup**: it matches `OVERLAP_LETTER_MAP`'s A-P, which comes from the same Hi-Res Enumerations spec, and keeping the check pure preserves `resolve_stopbar_target`'s use inside `ShapeConfig.relevant_phases()`/`relevant_overlaps()` with no DB handle. A test asserts the two ranges stay equal so they can't drift apart. The 1-16 bounds were already hardcoded in four places in the calibration GUI (`video/calibrate.py`), plus a duplicate `"A" <= x <= "P"` overlap-letter test — all five now import the shared constants / test membership in `OVERLAP_LETTER_MAP` per CLAUDE.md §5, and the dialog prompts derive their range text rather than spelling it out. No stored shape CSV was affected: the corpus has no `*_shapes.csv` with an out-of-range phase (none exist yet), so nothing that previously loaded now fails. Covered by boundary/out-of-range cases in `tests/data/test_video_shapes.py` (the old `test_phase_number_is_not_range_checked`, which pinned the looseness, is replaced); full suite green at 313 passed.
